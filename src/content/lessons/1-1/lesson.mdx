## Why this lesson comes first

Every architecture in this course sits on one mechanism: the **agentic loop**. Coordinators, subagents, hooks, MCP tools, and escalation handoffs are all ways of shaping what happens inside it. The Agent SDK, Claude Code, and the SDK's tool runner each run this loop for you, but the exam expects you to know what they're doing underneath. Several of the guide's anti-patterns are bugs in exactly this loop.

This lesson covers Task Statement 1.1: how the loop works, how tool results flow back to the model, who decides what happens next, and the three wrong ways to decide the loop is finished.

## The loop in one picture

A single API call gets one response. An agent is a program that keeps calling the API until the model says it's done:

Two things drive this: the `stop_reason` field on every response, and the conversation history you send back on every request.

## stop_reason is the control signal

Each response from the Messages API reports **why the model stopped generating**. For the loop, two values matter most:

| stop_reason | What it means | What your loop does |
|---|---|---|
| `"tool_use"` | The model wants one or more tools run before it can continue | Execute the tools, append results, call the API again |
| `"end_turn"` | The model finished its turn naturally | Exit the loop; the response is the answer |

The API has other values, and a production loop shouldn't treat them as success:

| stop_reason | What it means |
|---|---|
| `"max_tokens"` | Output hit your `max_tokens` cap. The response is truncated, possibly mid-sentence or mid-tool-call. |
| `"stop_sequence"` | Output hit a custom stop sequence you configured. |
| `"pause_turn"` | A server-side tool loop (such as web search) hit its iteration limit. Send the response back as-is so the model can continue. |
| `"refusal"` | The model declined the request. |
| `"model_context_window_exceeded"` | The response filled the model's context window. Treat it as truncated. |

<Callout type="exam">
The guide's task statement is explicit: the loop **continues when `stop_reason` is `"tool_use"` and terminates when `stop_reason` is `"end_turn"`**. If an answer option decides "are we done?" any other way, it's almost certainly a distractor.
</Callout>

## Tool results are how the model learns what happened

The API is **stateless**. Claude doesn't remember the previous request. Everything the model knows about the task so far comes from the `messages` array you send. So when a tool runs, the model only learns the result if you put it in the history.

Each iteration adds two messages:

1. **The assistant's turn, unchanged.** Append the full `response.content`, not just its text. It contains the `tool_use` blocks, each with an `id`, a tool `name`, and an `input`.
2. **A user turn containing the results.** One `tool_result` block per `tool_use` block, each carrying the matching `tool_use_id`.

```json
{ "role": "assistant", "content": [
    { "type": "text", "text": "Let me look up that order." },
    { "type": "tool_use", "id": "toolu_01A", "name": "lookup_order",
      "input": { "order_id": "4417" } }
]}
{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A",
      "content":
      "{\"status\": \"delivered\", \"delivered_at\": \"2026-09-12\"}" }
]}
```

On the next request, the model sees its own tool call **and** the result, and reasons about what to do next. The guide phrases this as appending tool results to the conversation history "so the model can reason about the next action."

### Three rules that keep the history valid

- **Every `tool_use` gets exactly one `tool_result`**, matched by ID. That includes failures: return the error as a `tool_result` with `is_error: true` and a useful description instead of dropping it. (Lesson 2.2 covers how to structure those errors.)
- **Parallel calls come back together.** A single response can contain several `tool_use` blocks, for example looking up two orders at once. Run them (concurrently if you like), then return **all** the results in **one** user message. Splitting them across several messages breaks the turn structure and teaches the model to stop making parallel calls.
- **Append the whole assistant content.** If you keep only the text, you lose the `tool_use` blocks, and the next request fails because your results reference IDs that aren't in the history.

## A worked trace

A customer writes: *"Where's order 4417? If it's late I want a refund."* The agent has `lookup_order` and `check_refund_eligibility` tools.

| Iteration | What the model returns | stop_reason | Messages after |
|---|---|---|---|
| 1 | Text "Let me look that up." **plus** `tool_use` lookup_order(4417) | `tool_use` | 3 (user, assistant, tool_result) |
| 2 | `tool_use` check_refund_eligibility(4417) | `tool_use` | 5 |
| 3 | "Your order arrived Sept 12, two days late. You qualify for a refund of $38.50…" | `end_turn` | 5 → answer returned |

Look closely at iteration 1: the response contains **text and a tool call**. The model often narrates before acting. That's why "the response has text, so we're done" is a bug, not a shortcut.

Also notice that nobody hard-coded "call lookup_order, then check_refund_eligibility." The model chose each step based on what it had learned so far.

## Model-driven decisions vs pre-configured sequences

The guide distinguishes two ways to decide what happens next:

- **Model-driven decision-making:** Claude reasons over the current context and picks the next tool (or decides it's finished). This is what makes an agent an agent. It handles requests you didn't anticipate, skips steps a case doesn't need, and adapts when a result is surprising.
- **Pre-configured decision trees or tool sequences:** your code decides the order ("always call A, then B, then C"). Predictable, but brittle for high-ambiguity work: every new request type needs a new branch.

For open-ended tasks the exam favors model-driven loops. It **doesn't** say code should never constrain the model. The rule you'll see in Lessons 1.6 and 1.7 is:

> Let the model decide *what to do*. Use code to guarantee the few things that *must always hold*.

For example, "refunds require a verified customer ID" belongs in a programmatic prerequisite, because a prompt instruction that works 99% of the time fails 1% of the time. That's a guardrail around the loop, not a replacement for it. Replacing model-driven selection with a fixed script throws away the adaptability you built an agent for.

## A reference loop

This is the manual loop in Python using the Anthropic SDK. It's deliberately explicit so you can see every step. In practice, the SDK's tool runner or the Claude Agent SDK runs this loop for you.

```python
import anthropic

client = anthropic.Anthropic()

def run_agent(user_input: str, tools: list,
              max_iterations: int = 25) -> str:
    messages = [{"role": "user", "content": user_input}]

    # max_iterations is a safety backstop, NOT the stopping rule
    for _ in range(max_iterations):
        response = client.messages.create(
            model="claude-opus-5-5",
            max_tokens=16000,
            tools=tools,
            messages=messages,
        )

        if response.stop_reason == "end_turn":
            return "".join(
                b.text for b in response.content if b.type == "text"
            )

        if response.stop_reason != "tool_use":
            # max_tokens, refusal, etc. are not success. Surface them.
            raise RuntimeError(
                f"Agent stopped unexpectedly: {response.stop_reason}"
            )

        # 1. Keep the assistant turn intact (it holds the tool_use
        #    blocks)
        messages.append(
            {"role": "assistant", "content": response.content}
        )

        # 2. Run every requested tool; collect ALL results
        tool_results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                # execute_tool is your code
                output = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": output,
                })
            except Exception as err:
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": f"{type(err).__name__}: {err}",
                    "is_error": True,
                })

        # 3. Return them together in ONE user message
        messages.append({"role": "user", "content": tool_results})

    # Hitting the backstop means something went wrong: escalate,
    # don't pretend success
    raise RuntimeError("Agent hit the iteration backstop unfinished")
```

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

async function runAgent(
  userInput: string,
  tools: Anthropic.Tool[],
  maxIterations = 25, // safety backstop, NOT the stopping rule
) {
  const messages: Anthropic.MessageParam[] = [
    { role: "user", content: userInput },
  ];

  for (let i = 0; i < maxIterations; i++) {
    const response = await client.messages.create({
      model: "claude-opus-5-5",
      max_tokens: 16000,
      tools,
      messages,
    });

    if (response.stop_reason === "end_turn") {
      return response.content
        .flatMap((b) => (b.type === "text" ? [b.text] : []))
        .join("");
    }
    if (response.stop_reason !== "tool_use") {
      throw new Error(
        `Agent stopped unexpectedly: ${response.stop_reason}`,
      );
    }

    messages.push({ role: "assistant", content: response.content });

    const toolResults: Anthropic.ToolResultBlockParam[] = [];
    for (const block of response.content) {
      if (block.type !== "tool_use") continue;
      try {
        // executeTool is your code
        const output = await executeTool(block.name, block.input);
        toolResults.push({
          type: "tool_result",
          tool_use_id: block.id,
          content: output,
        });
      } catch (err) {
        toolResults.push({
          type: "tool_result",
          tool_use_id: block.id,
          content: String(err),
          is_error: true,
        });
      }
    }
    messages.push({ role: "user", content: toolResults });
  }
  throw new Error("Agent hit the iteration backstop unfinished");
}

## The three termination anti-patterns

The guide names three wrong ways to decide the loop is finished. Expect each to appear as a tempting answer option.

<Callout type="warning" title="1. Parsing natural-language signals">
Ending the loop when the text contains "I'm done," "Task complete," or "Final answer:". Wording varies, the model may say "done" about one sub-step while still planning more calls, and a customer's quoted message can contain the same phrase. `stop_reason` is a structured signal made for exactly this decision; don't reinvent it with string matching.
</Callout>

<Callout type="warning" title="2. Iteration caps as the primary stopping mechanism">
"Run 5 iterations, then return whatever we have." A cap that cuts off a legitimate 6-step task returns a half-finished answer as if it were complete, and a cap set high enough for every task is no longer a stopping mechanism. A cap **is** fine as a *safety backstop* against runaway loops, like `max_iterations=25` above. Reaching it should be treated as a failure to investigate or escalate, never as a normal finish.
</Callout>

<Callout type="warning" title="3. Treating assistant text as a completion indicator">
"If the response contains a text block, show it to the user and stop." As the worked trace shows, the model routinely writes text *and* requests tools in the same response ("Let me check that for you" plus a `tool_use` block). This bug makes agents announce they're about to act and then never act.
</Callout>

The fix for all three is the same: **branch on `stop_reason`.**

## How this shows up on the exam

- **Symptom → cause mapping.** "The agent says it will check but never does" points to text-as-completion. "The agent repeats the same tool call as if it never got the answer" points to results not being appended to history. "Long tasks return partial answers" points to an iteration cap used as the stopping rule.
- **Distractors that treat symptoms.** Raising `max_tokens`, prompt instructions like "don't write text before calling tools," or larger caps all leave the broken loop logic in place.
- **Scenario anchors.** The customer support scenario (Scenario 1) and developer productivity scenario (Scenario 4) both assume a correct loop. Questions about hooks, errors, and escalation build on it.

<KeyTakeaways>

- The loop: send → check `stop_reason` → on `"tool_use"` run tools and append results → repeat → stop on `"end_turn"`.
- The API is stateless. The model only knows a tool's result if you append the assistant turn **and** a `tool_result` (matched by `tool_use_id`) to the history.
- Every `tool_use` gets a `tool_result`, including failures (`is_error: true`). Return parallel results together in one user message.
- Model-driven tool selection is the default for open-ended work. Use code only to guarantee must-hold rules, not to script the whole path.
- Anti-patterns: parsing text for "done," iteration caps as the primary stop, and treating text content as completion. Caps are fine as a backstop that signals failure.
- `max_tokens`, `refusal`, and other non-`end_turn` stops aren't success. Handle them explicitly.

</KeyTakeaways>
